2. **The MCP spec goes stateless on July 28 — the handshake and session ID are removed, and every server we run has 13 days to be ready** ([blog.modelcontextprotocol.io](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)) — the release candidate is locked and the final spec publishes Jul 28. The `initialize`/`initialized` handshake is gone; protocol version, client info and client capabilities now travel in `_meta` on *every* request, with a new `server/discover` method for clients that want capabilities up front. The `Mcp-Session-Id` header and the protocol-level session are removed, so any request can land on any server instance — no sticky routing, no shared session store, plain round-robin works. Six SEPs deliver the change; extensions (MCP Apps, Tasks) become first-class, plus auth hardening and a real deprecation policy. Tier 1 SDKs are expected to ship support inside the ten-week validation window. **Applicable: YES** — this is the floor moving under bullets 1 and 3. Not breaking news (the RC locked in May), but it earns the slot today because it is 13 days out and nobody has checked our surface against it. Every MCP server The Construct depends on — and every one we'd put in front of a PRAGMA client — either follows its SDK through the window or breaks. Concrete action pairs with `/doctor`: prune the fleet first, then pin which survivors are on Tier 1 SDKs and which are hand-rolled and now our problem. The stateless move is also quietly good news for us — it makes a client-hosted managed MCP dramatically cheaper to run.
