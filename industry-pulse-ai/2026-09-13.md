1. **A SANDBOXED AGENT COULD TURN OFF ITS OWN SANDBOX WITH ONE SHELL COMMAND — AND THE HARNESS LOGGED THE POLICY CHANGE AS `source: {kind: 'user'}`, BECAUSE IT COULD NOT DISTINGUISH THE AGENT'S SHELL FROM THE HUMAN AT THE KEYBOARD (CVE-2026-82533, CVSS 9.4)** ([www.ox.security](https://www.ox.security/blog/cve-2026-82533-deepseek-harness-ai-agent-sandbox-escape/)) — OX Research primary, PUBLISHED 8 SEPTEMBER 2026 (page dateline and `article:published_time` both read); disclosure timeline on the page: confirmed by execution and reported to VulnCheck as CNA **24 Aug**, fixed in DeepSeek Harness **0.1.2-alpha.1 on 27 Aug**, re-tested and confirmed remediated **30 Aug**, CVE published **8 Sep**. Affected: `dsh` **0.1.1-rc.2 and earlier**. CWE-807, *Reliance on Untrusted Inputs in a Security Decision*. The mechanism, in the researchers' own terms: DeepSeek Harness exposed its agent-control API on a local HTTP port (`127.0.0.1:3080`) with NO authentication, and a single function, `isTrustedApiRequest`, decided trust by reading the client-supplied **`Host` request header** — never comparing it against the connection's actual peer address. A browser cannot lie about `Host`, so the check did defeat DNS rebinding, which is what it was written for; a client not subject to browser restrictions simply claims to be loopback. The second half is the one that matters: the OS sandbox (bubblewrap / Landlock / Seatbelt) **confined the filesystem but left networking open** — bubblewrap was passed `--unshare-pid` but NOT `--unshare-net`, and the Seatbelt profile used `(allow default)` with `(deny file-write*)` layered on top — so loopback was reachable from inside the sandbox, while ordinary `bash` tool calls required no approval at all (approval governed sandbox-escalation *requests*, not routine execution). Net effect on SHIPPED DEFAULTS, with no network exposure, no credentials and no config changes: the agent runs one `curl` at its own harness and elevates its session to `danger-full-access` with approval set to `never`; every command after that runs unconfined and unprompted. OX ran a matched control on the same host — two sessions, same preset, same command, one having made the `curl` first — and the escaped session wrote outside its workspace to `/home/ubuntu` while the confined session was blocked, proving the sandbox had been actively enforcing before the escape. **No `approval/request` event appears anywhere in the session log.** A second path: wherever that port was reachable through a tunnel, reverse proxy, SSH forward or editor port-forward, an unauthenticated REMOTE attacker could take full control of the agent and download **every stored conversation** with no API key and no model call. Scale context from the same primary: `dsh` is DeepSeek's open-source local-first coding-agent harness, released **August 2026**, tagline "Everything is a Plugin," and it passed **215,000+ GitHub stars within weeks**. **Applicable: YES** — YES, and it is the lead because one line of it is the best evidence this report has ever had for a claim it has been making on vibes. **(1) THE HONEST SCOPE FIRST, BEFORE ANY ALARM.** DeepSeek **Harness** is a tool; `OPENROUTER_MODEL=deepseek/deepseek-v4-flash` — the item this report has carried unresolved for two days, live in `~/.hermes/.env` on the executor that holds the DreamHost deploy key, GitHub write and GSC — is a MODEL ROUTE. They share a vendor name and nothing else. This CVE is **not** automatically ours, and saying otherwise would be exactly the manufacture error the morning fire warned about. The action is a CHECK, not a patch: confirm `dsh` is installed nowhere on the Mac or the render node, which is one `which dsh` and one `ls ~/.dsh`. **(2) THE LINE THAT IS WORTH MORE THAN THE CVE.** The policy change was recorded as `source: {kind: 'user'}`. The harness could not distinguish the agent's own shell from the human at the keyboard — so its audit log sincerely attributed an agent's self-escalation to Bobby. That is arXiv 2609.00267's **CONFUSED DEPUTY** adversary, observed in production, in a tool with 215,000 stars, on default settings. It is also the precise mechanism by which our own stack would fail: Hermes executes shell scripts dropped into `~/.hermes/scripts/` with the deploy key, and nothing in that path distinguishes a script Bobby asked for from a script a skill file asked for. We have written that sentence three times as a worry. It is now a citation. **(3) THE DESIGN LESSON IS FREE AND GENERALIZES PAST THIS BUG.** Two controls were each individually reasonable — deny file writes; require approval for escalation — and the gap between them was the whole vulnerability, because nobody asked what the confined process could still REACH. Our sandbox story is the same shape: the Cowork shell is isolated and the mounts are enumerated, but the question "what can the confined thing still reach, and does reaching it let it rewrite its own limits" has never been asked in writing. **(4) PRAGMA, one question wide.** "Can your agent harness tell your agent apart from you in its own audit log?" is answerable in a day, fails for most shops, and is the cheapest possible opening for the security-adjacent operator SKU the 3 September Tenable item priced.

3. **THE MCP MAINTAINERS' OWN ROADMAP CONFIRMS WHAT THE PAPER FOUND EMPIRICALLY: MCP AUTHORIZATION "IS BUILT AROUND A PERSON APPROVING ACCESS IN A BROWSER," AND THE FIX IS NAMED STANDARDS (DPoP, WORKLOAD IDENTITY FEDERATION, ID-JAG) — SO STANDING ACTION (f) SHOULD NOT BE INVENTED FROM SCRATCH** ([blog.modelcontextprotocol.io](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/)) — Model Context Protocol blog, "The New MCP Roadmap," by lead maintainers David Soria Parra and Den Delimarsky, **PUBLISHED 22 AUGUST 2026** (`article:published_time: 2026-08-22`, modified 23 Aug — read off the page, three weeks old, carried deliberately). It is not a critique; the maintainers say it themselves, in a roadmap priority area titled **"Agent identity and enterprise-ready security"**: *MCP authorization today is built around a person approving access in a browser. Two further items from the same primary bear directly on our backlog. **PROGRESSIVE DISCOVERY**, under "Improved primitives," states the problem in our exact terms: *Connecting to a server with a hundred tools means the model pays for that entire surface before the user has asked a single question, and tool selection tends to get worse as the list grows* — so a server will be able to "offer a small entry point and reveal more of its catalog as the conversation narrows." And the shipped **2026-07-28 specification** is more consequential than this report has ever recorded: protocol-level sessions and the initialization handshake are **gone** (SEP-2575, SEP-2567) so servers scale horizontally without holding state, `server/discover` lets a client learn versions and capabilities before doing anything else, list results are cacheable (SEP-2549), Tasks moved into an official extension (SEP-2663), and Multi Round-Trip Requests (SEP-2322) replaced server-initiated requests so elicitation works on stateless servers. **Applicable: YES** — YES, and it is the cheapest item on the page because it mostly tells us what NOT to build. **(1) DO NOT INVENT A CREDENTIAL SCHEME.** Standing action (f) — "put the boundary in the credential" — has been a slogan for two days and gained eight requirements this morning. Hermes today is the anti-pattern the roadmap names in one phrase: **a pasted long-lived token** — one deploy key, no scoping, no rotation record. The correct next step is not a homegrown design, it is reading RFC 9449 and asking whether our own executor can hold a proof-of-possession key at all. **(2) PROGRESSIVE DISCOVERY VALIDATES THE ECONOMY COLUMN.** Standing action (c)'s ECONOMY item — `/skill-doctor`, one command, still unrun against ~130 skills — has been the easiest thing on the list to postpone because it sounded like tidying. Run the command before the platform makes the problem invisible and we lose the chance to know our own number. **(3) THE STATELESS SPEC IS A PLANNING FACT WE MISSED.** Sessions and the init handshake being gone is why a remote MCP server is now "no different from any other HTTP workload" — which is precisely the property that makes the cloud migration in this morning's bullet 1 cheap for Anthropic to ship. Two vendor-side changes we did not choose, pointing the same direction, one of them three weeks old and unrecorded until now. **(4) PRAGMA.** "The protocol does not yet carry agent identity, and here is the maintainers' own roadmap item saying so" is a true, sourced, non-alarmist sentence to say to any client being sold MCP connectors — and unlike most security talk, it comes with a date and a fix.
