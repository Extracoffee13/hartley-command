The other four areas: agentic messaging primitives (server-initiated events — webhooks and channels, "so clients aren't left polling for results" — and maturing the Tasks extension SEP-2663 into the spec proper); HTTP-native transport unification, extending Streamable HTTP to local servers over stdio so there is one transport rather than two; **agent identity and enterprise-ready security**, which states the problem plainly — "MCP authorization today is built around a person approving access in a browser… more and more of the callers are agents running as cloud workloads with their own identity, acting on behalf of a user who isn't present, or delegating narrower authority to sub-agents" — to be addressed via DPoP (RFC 9449), Workload Identity Federation, and the ID-JAG grant behind Enterprise-Managed Authorization, which the post notes is **now stable**; and SDK conformance. **Applicable: YES.** Progressive discovery is the vendor-side answer to the same measurement `/doctor` and `/usage` give us on the client side — this morning's bullet 2 — and the two are complementary, not redundant: `/doctor` tells us which of our ~130 skills are dead weight, progressive discovery changes whether a live one costs anything until it is needed. The agent-identity area is the more urgent read for a fleet where Hermes holds the only credentialed deploy path: "a person approving access in a browser" is exactly how our credentials work today, and the protocol is openly saying that model does not survive contact with sub-agents delegating authority.

4. **THE READING QUEUE, NARROWED FROM ARCHITECTURE TO MEASUREMENT — three tool-selection papers that turn "we have too many skills" from an intuition into a number, one of them empirically grounded on Claude** ([arxiv.org](https://arxiv.org/abs/2608.04719)) — All out of window; named because bullet 2's progressive-discovery effort and this morning's `/doctor` action both need something to be measured against. **2608.04719, *Diagnosing Tool-Selection Reasoning in LLM Agents with Canary Tools*** (submitted 5 Aug 2026, Anand & Chattaraj) — primary abstract read. Plants deliberately-engineered decoy tools in an agent's MCP tool set and scores which ones it takes, under a six-type taxonomy: semantic decoys, parameter traps, **capability mirages**, prerequisite blindness, temporal decoys, granularity traps. 8,640 runs across eight models plus a 2,880-run ablation, dual independent judges at Cohen's κ = 0.75. Three findings that bear directly on how this fleet is configured: per-task canary susceptibility ranges **about 36x across models** and is lowest for Claude Opus 4.8; **capability tier alone does not predict safety** — the most susceptible hosted model is mid-tier, and within one provider the cheaper model can be the safer one; and *capability mirages* — a tool that advertises something it cannot do — are the one type that "most reliably trap frontier models" while the other five are largely inert on strong models. Softening each decoy's give-away phrasing left frontier susceptibility essentially unchanged, so the probes measure reasoning rather than phrase-spotting. Susceptibility predicts task failure at Spearman ρ = −0.34, and the framework, schemas, tasks and logs are released. Alongside it, **2605.24660, *How Many Tools Should an LLM Agent See? A Chance-Corrected Answer***, which evaluates registries from 20 to 3,251 tools, and **2606.16364, *Looking Is Not Picking: An Attention-Segment Account of Tool-Selection Failures***. **Applicable: MAYBE**, but the sharpest MAYBE this report has carried, because the canary method is directly runnable here and needs no vendor cooperation: our ~130 skills include several whose descriptions promise more than the skill delivers, which is the definition of a capability mirage — the one decoy class that catches strong models. Order stands: `/doctor` for the dead-weight count first, `/usage` for the attribution, then canaries to find out whether the *live* skills are being selected correctly. Architecture papers (2606.20631, 2606.30005) stay behind all three.

**PRAXIS lesson:** Three days, three archive audits, three falsified standing claims — and today's two were both on the pillars this report calls NULL. That is no longer a run of bad luck; it is a structural finding about how this report fails. **Its nulls are not observations about the world. They are the shape of its channel list, reported as if they were the shape of the world.** "MCP has been quiet eight weeks" meant *the specification release page has no new entry* — while the protocol's maintainers published a roadmap on the blog feed whose named priority is the precise problem this fleet has. "The sign trade has no API layer, twenty-one days running" meant *nothing crossed the searches I ran* — while a 60,000-detail permitting-and-fabrication dataset with open nonexclusive API licensing sat five weeks old in the trade press that covers Brand 9's own industry. Both nulls were repeated daily with increasing confidence, and repetition was doing the work that evidence should have. So the rule that replaces "audit the archive of any new channel" is stronger and costs more: **a null must name the surface it was read from, or it must not be published.** "No MCP news" is not a finding; "no new entry on the MCP specification release page, which is one of four MCP surfaces and not the one that carries roadmap or governance work" is a finding, and it is one that visibly invites the missing check. A null with its surface named is falsifiable in a sentence. A bare null is a claim about everything, defended by nothing, and it hardens every day it is restated. Second, on the day's near-miss: date failure #9 was the most dangerous of the nine, because the content was *true* — real fixes, accurately described, verbatim from the vendor — and only the date was wrong. Staleness announces itself; **reordering does not.** A third-party aggregator that returns four-day-old release notes under today's heading produces something indistinguishable from good reporting, and the only defence that worked today was parsing the primary's own `<Update label=...>` headings rather than reading anyone's prose about them, including the primary's. Third, the two corrections stack into one action rather than two: bullet 2 says the protocol is building progressive discovery because a hundred tools cost the model everything before the first question; bullet 4 says the failure mode that survives on frontier models is the **capability mirage**, a tool advertising what it cannot do. This fleet has ~130 mostly self-authored skills, written over months, several of which promise more in their description than they deliver. That is not a hypothetical exposure. It is the single documented weakness of strong models, sitting in our own corpus, measurable today with a released framework — and it is a better reason to run `/doctor` this week than context cost ever was.
