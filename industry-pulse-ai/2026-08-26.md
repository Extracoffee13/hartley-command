1. **Anthropic merged Claude's chat memory and Cowork memory into ONE store yesterday — the vendor shipped the consumer-tier form of Dreams less than 24 hours after this report logged Dreams as its largest corpus gap** ([techcrunch.com](https://techcrunch.com/2026/08/25/claude-cowork-finally-remembers-what-you-told-the-app-in-chat/)) — On Tuesday Aug 25 Anthropic announced it is merging the memory systems used by Claude chat and Claude Cowork, so what Claude learns in one surface is available in the other rather than requiring a re-brief when work moves from thinking to doing. Three details carry most of the weight. Memory is now written INCREMENTALLY — Claude adds topics as the conversation proceeds instead of summarising a conversation once it ends — which is what makes a still-running chat visible to a Cowork session. The store is INSPECTABLE and EDITABLE: users can read, edit or delete what Claude has retained, per topic. And there is a stated sensitive-data boundary — health, race, ethnicity, religion, politics and gender identity are excluded by default behind an opt-in 'include sensitive topics in memory' toggle that notifies on save, while government ID, SSNs, criminal history and immigration status are never stored. It is on by default for Free, Pro and Max across web, desktop and mobile, with an app update required on iOS and Android. **Applicable: YES** — YES, and the timing is the finding. Yesterday's 14:00 bullet 6 logged Dreams — Anthropic's scheduled offline memory consolidation for Managed Agents, shipped in MAY — as the largest gap this corpus has ever produced, on the grounds that Bobby had independently hand-built the same machinery (praxis-inbox.md as the store, self-improving-loop as the consolidation pass, this report as the transcript) while the vendor's own release notes carried it twice. Within a day the vendor shipped the surface-level version of the same idea into the exact product Bobby works in. That is not luck; it is what happens when you start reading a thread instead of restarting it. Three concrete reads for The Construct. First, incremental cross-surface memory partially dissolves a real friction in Bobby's setup: CLAUDE.md is a hand-maintained working cache whose entire purpose is to stop Claude re-asking settled questions — the locked V4 dashboard rule exists verbatim because that question kept recurring — and a memory that writes as it learns and is shared across surfaces reduces how much of that has to be carried by a file Bobby maintains himself. Second, the editable/inspectable store is the more important half operationally: a memory you cannot read is a memory you cannot correct, and our whole PRAXIS discipline is built on correction, so an auditable store is compatible with the loop where an opaque one would not be. Third, the caveat has to travel with the recommendation, because it is the same one yesterday's Dreams bullet raised and it is now larger: memory that persists across chat AND Cowork is a cross-surface persistence surface, and anything that reaches it reaches the premises of every later session in either product. Client work runs through these sessions. The move is to inspect what is in the store before trusting it, not to assume the default boundary matches ours.

2. **Claude Code shipped per-LOOP cost accounting in /usage — runaway scheduled jobs are now visible as a line item, which is the first time this ecosystem's own token spend has been measurable** ([releasebot.io](https://releasebot.io/updates/anthropic/claude-code)) — The latest Claude Code release adds a Loops breakdown to /usage: per-loop run count, total tokens, tokens per run, and last run, framed by Anthropic as making runaway or chatty /loop tasks easy to spot. Shipped in the same release: a keyless sign-in path under /login -> Anthropic Console ('Sign in with your Console account', marked recommended) so organisations that forbid API keys can authenticate without minting one; cloud sessions now show plugins synced from claude.ai as name@synced, which work with claude plugin enable/disable <name>@synced and never override a same-named plugin you installed locally; a /claude-api upgrade command that migrates Python projects from anthropic 0.x to 1.x with the reference updated for 1.x semantics (timeouts use anthropic.Timeout, not httpx.Timeout); Alpine/musl builds that finally load the native image-paste, clipboard and audio-capture add-ons; and a fix for a startup crash on glibc 2.44 distributions including Arch, CachyOS and Fedora Rawhide. **Applicable: YES** — YES on the first item, and it is more consequential than a changelog line suggests. The Construct runs a fleet of scheduled loops — this Pulse scan, lens-daily-scan, the Mallard visibility pass, the B9 site-health sentinel, the Hermes cron ticker and worker queue — and until now their token cost has been an aggregate with no per-job attribution. 'Tokens per run' plus 'last run' is simultaneously a cost breakdown AND the heartbeat this report prescribed on 08-24 and again on 08-25: a job whose last run is three days stale is a dead job, and the same panel that shows the spend shows the staleness. That is a cheaper version of the heartbeat than building one, and it should be read before it is built. It also lands directly on yesterday's bullet 1: if the fix for front-loaded skill files is on-demand loading, per-loop token accounting is how we find out whether the fix worked, because b9-answer-page-factory and the vironbox-* family being paid for in full on every turn is exactly the kind of chatty-loop cost this breakdown surfaces. The second useful item is name@synced. Bobby's plugin and skill fleet is large and increasingly cross-surface, and a naming scheme that guarantees a claude.ai-synced plugin never silently shadows a locally installed one of the same name removes a class of failure that would be very hard to diagnose from symptoms. Keyless Console sign-in is not a Construct problem today, but it is a PRAGMA selling point: a client whose IT forbids API keys is no longer a client we cannot onboard.

3. **CORPUS GAP — a paper argues the multi-agent FRAMEWORK is the thing to delete: numbered folders and markdown files, 2k-8k tokens loaded per stage, one agent playing every role** ([arxiv.org](https://arxiv.org/abs/2603.16021)) — arXiv 2603.16021, 'Interpretable Context Methodology: Folder Structure as Agentic Architecture' (Jake Van Clief and David McDermott; 28 pages, 5 figures, 2 tables, 54 references, open-sourced under MIT at github.com/RinDig/Interpretable-Context-Methodology), replaces framework-level orchestration with filesystem structure. Numbered folders are stages; plain markdown files carry the prompt and context telling a single agent what role to play at that step; local scripts do the mechanical work that needs no model at all. The claimed constraint is the load-bearing part: each stage loads only the context it needs, typically two thousand to eight thousand tokens, on the argument that this avoids the degradation that occurs when a model processes a long context full of irrelevant material. The stated scope is deliberately narrow — sequential workflows where a human reviews output at each step — and the claim is that for those, a multi-agent framework is engineering overhead the problem does not require. **Applicable: YES** — YES, logged as a corpus gap: the arXiv ID, the title and the phrase 'folder structure' return zero matches across all 57 files, in a corpus that has carried ACE (2510.04618) repeatedly, 2603.09619 three times, and 2602.05447 on file-native context. It matters because it is the third independent answer to the same question this month and all three converge: Anthropic deferred reference docs out of the always-loaded context (yesterday's bullet 1, 200k -> 25k), ACE said do not compress because compression drops the insight, and this paper says scope the load to the stage. None of the three says write shorter. All three say load less at once. Our skill library is the artifact that should change, and this paper describes what it nearly already is — a directory of markdown files, each carrying triggers, hard rules and a decision tree, read when the branch is taken. The gap between our library and ICM is that our files are not stage-scoped and not budgeted; a b9-answer-page-factory run does not load a build stage, it loads the entire manual. The honest caveats are two and they are load-bearing. The scope is sequential human-reviewed workflows, which describes the answer-page factory and the render pipeline well and describes Hermes' credentialed concurrent execution badly, so this is not a replacement for the worker queue. And it is a methodology paper with an open-source implementation, not a benchmarked result against a framework baseline — the 2k-8k figure is a design constraint the authors chose, not a measured optimum, and should be read as an argument rather than as evidence.
