1. **Correction to yesterday's brief — the Jul 28 MCP spec is *not* a breaking deadline, and the beta SDKs to test it have been out since Jun 29** ([blog.modelcontextprotocol.io](https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/)) — the official SDK announcement is explicit: "for existing clients and servers nothing breaks today, and nothing breaks on July 28 either. This is merely the date when the normative specification text is published and is not a switch-off for any implementers relying on the current protocol version." Betas are available for all four Tier 1 SDKs — Python `mcp` v2 (`2.0.0b1`), TypeScript v2 (split packages, ESM-only, `@beta`), Go (`v1.7.0-pre.1`), C# (`2.0.0-preview.1`) — and opting in is deliberate at every step: unpinned installs still resolve to stable, TypeScript/Go don't change what they speak over HTTP until you wire the transport, and clients speaking `2026-07-28` fall back to the `initialize` handshake against `2025-11-25` servers. The release candidate is now published and confirms the shape ([blog.modelcontextprotocol.io](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)): stateless core, `Mcp-Method` and `Mcp-Name` headers so gateways and rate-limiters route without inspecting the body, `ttlMs` and `cacheScope` on list/read results, extensions (MCP Apps, Tasks) first-class, and a formal deprecation policy. Standard error codes change (missing resource returns JSON-RPC `-32602`, not the MCP-custom `-32002`). **Applicable: YES** — our Jul 15 brief said every MCP server we run "has 13 days to be ready" and "either follows its SDK through the window or breaks." That was wrong, and it was wrong in the direction that manufactures urgency. Nothing switches off. The real action is smaller and duller: add `mcp>=1.27,<2` upper bounds now so the stable Python v2 doesn't surprise us, pin exact versions if we test a beta, and check whether anything in our fleet string-matches `-32002`.

2. **Claude Code 2.1.210 + 2.1.211 — security and memory-integrity fixes, then subagent text streaming lands 25 hours later** ([code.claude.com/docs/en/changelog](https://code.claude.com/docs/en/changelog)) — 2.1.210 shipped four fixes that hit The Construct specifically: the Agent tool hardened against indirect prompt injection via content a subagent read; `isolation: 'worktree'` subagents no longer able to run git-mutating commands against the main repo checkout; the `ultracode` keyword opt-in no longer firing on non-human-originated input such as webhook payloads and relayed PR comments; and memory writes that leave a MEMORY.md index over its read limit now producing an explicit error instead of silently truncating. Alongside: plugin-provided MCP servers no longer torn down when MCP servers re-sync mid-session, unmatched `$1`/`$2` placeholders in skills and commands preserved instead of silently stripped, auto-mode permission classifier defaulting to Sonnet 5 for external sessions. **2.1.211 followed roughly 25 hours later (Jul 15)** and adds `--forward-subagent-text` plus `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT`, which forwards subagent assistant text *and thinking* into `stream-json` output, correlated to the parent via `parent_tool_use_id` ([dev.classmethod.jp](https://dev.classmethod.jp/en/articles/20260711-cc-updates-v2-1-211/)). Previously, under `claude -p --output-format stream-json`, only a subagent's final returned result was observable — everything it reasoned on the way there was dark. Stated use cases: streaming subagent progress to logging infrastructure during CI, custom frontends over the Agent SDK, and debugging subagent reasoning directly from the stream. **Applicable: YES** — the MEMORY.md fix is the one to sit with: `~/.hermes/memories/MEMORY.md` is our index, it grows every day, and until 2.1.210 an oversized index truncated *silently* — agents may have been reading a partial memory with no error raised. The worktree-escape fix guards exactly the boundary the Hermes-only-GitHub-credential rule exists to protect. And `--forward-subagent-text` is the direct instrument for a gap we have: every scan and brief this fleet produces is written by subagents whose reasoning we have never been able to see, only whose conclusions we accept. Yesterday's fabricated MCP deadline was produced somewhere inside that dark region.

3. **Cowork on web and mobile runs on Anthropic-hosted remote sessions — scheduled tasks now run with no device online at all** ([claude.com/blog](https://claude.com/blog/cowork-web-mobile)) — announced Jul 7 and rolling out in beta over several weeks starting with Max: Cowork sessions move to claude.ai and iOS/Android, saved to your Claude account, with work continuing in the background after you close the laptop. The execution model is the change, not the surface: remote sessions hosted on Anthropic's servers can keep working — and run scheduled tasks — with no device online. Related, same day: Claude Code and Cowork went to public beta in a FedRAMP High environment via Claude for Government Desktop ([claude.com/blog](https://claude.com/blog/bringing-claude-code-and-claude-cowork-to-government)). **Applicable: YES** — a structural fix for a constraint we designed around rather than solved. `lens-daily-scan` carries "survives Cowork being closed overnight" in its own description, and the multi-fire 5:34/9:34/13:34 schedule with idempotent skip exists precisely because we could not trust a fire to happen when the machine was asleep. Remote-hosted scheduled tasks remove the premise. Worth testing before we simplify anything — but if it holds, the whole multi-fire-plus-skip pattern is scaffolding we can take down.

4. **Oak exits stealth with $60M seed to govern non-human identities — the agent permission problem is now a funded category** ([techcrunch.com](https://techcrunch.com/2026/07/15/backed-by-60m-in-funding-oak-steps-out-of-stealth-to-fix-the-identity-mess-that-ai-agents-are-making-worse/)) — founded by Shai Morag and Tal Marom, co-led by Accel, Greylock, and CRV, already GA and deployed in enterprises. Oak replaces the fragmented legacy IAM stack with a single control plane governing every identity — human, machine, or AI agent — building a live identity graph from raw evidence via an AI connector framework spanning on-prem, cloud, SaaS, and homegrown apps. The founding research is the tell: 100+ CISOs and IAM leaders reported the same three problems — too many disconnected tools, no visibility into how access is actually used, and no way to govern AI agents at all ([prnewswire.com](https://www.prnewswire.com/news-releases/oak-raises-60m-in-seed-funding-to-build-the-ai-native-identity-operating-system-302826349.html)). **Applicable: YES** — the same thread as Rafay's managed MCP server from Jul 15, now with a seed round attached and a sharper frame: the unit of governance is the *identity*, not the server. The Construct runs a fleet of agents against client systems with credentials that were designed for humans. "No way to govern AI agents" is not a market gap someone else has — it is a description of our own posture, and PRAGMA cannot sell an operator wedge into a client's stack without an answer to who the agent *is* when it authenticates.
